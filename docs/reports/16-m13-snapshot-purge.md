# گزارش 16: M13 — snapshot، purge، هرس لاگ، جریان نسخه

- تاریخ: 2026-11-21 · تگ: `m13`
- وضعیت: **بخش خودکار سبز.** هرس واقعی روی سرور شخصی (۳۰ روز) و بکاپ قبل از اولین هرس واقعی با مالک.

## طراحی
- **snapshot:** opی با فریم `snap` (حالت یک موجودیت: رجیسترها با HLCی که نوشتشان + حالت Yjs) و فیلد envelope `cov` (بالاترین seq که اثرش در snapshot هست). **قاعدهٔ ایمنی** در `Client.writeSnapshot`: فقط وقتی cursor به head رسیده **و inbox خالی است** (پس همهٔ opهای ≤ cov اعمال شده و هیچ opی برای schema جدیدتر نگه داشته نشده)؛ بررسی و نوشتن در یک تراکنش. هر ساعت، حداکثر ۱۰ سند از فهرست «سند با ≥ ۱۰۰ op بدون پوشش» (`GET …/snapshots/candidates`؛ سرور فقط می‌شمارد).
- **pull فشرده** (`compact=1`؛ دستگاه تازه همیشه): opی که snapshot همان سند با `cov ≥ seq` و **`sv ≥ sv` آن op** پوشانده نمی‌آید؛ **opی با sv بالاتر از snapshot هرگز پنهان نمی‌شود** (آزمون Go).
- **هرس:** فقط opِ بدون cov، **قدیمی‌تر از ۳۰ روز** و پوشش‌داده‌شده طبق همان قاعده؛ snapshot و opهای بالاتر از cov هرگز. `workspace.pruned_through` بالاترین seq حذف‌شده؛ pull با `after` داخل ناحیهٔ حذف‌شده → `410 resync_required`؛ کلاینت cursor را صفر می‌کند و pull فشرده می‌گیرد (حالت محلی پاک نمی‌شود). هر ساعت؛ **پیش از هرس بکاپ `VACUUM INTO` (حداکثر روزی یک بار)** و اگر بکاپ شکست بخورد **هیچ هرسی انجام نمی‌شود**.
- **purge:** فیلد envelope `pg: 1` (انحراف از ADR-0005: سرور محتوای `p` را نمی‌خواند، پس نشانگر purge در envelope آمد؛ **نیازمند تأیید معمار**)؛ سرور همهٔ opهای دیگر آن doc را حذف می‌کند، `purged` ثبت می‌شود و opهای دیرآمده status `purged` می‌گیرند. کلاینت در همان تراکنش `Tx.purgeEntity` (رجیسترها، رویدادها، سند، updateها؛ روی Memory، IndexedDB و SQLite دسکتاپ با conformance). UI: سطل ← «حذف دائمی» و «خالی کردن سطل» با تأیید؛ زیرصفحه‌ها هم می‌روند.
- **426:** نشانگر «این نسخهٔ برنامه قدیمی است» با دکمهٔ بارگذاری دوباره در نوار بالا؛ opها نگه داشته می‌شوند. **Service Worker نیامد** (ROADMAP: «اگر در M5 نیامد»): پوستهٔ PWA با SW هنوز نیست؛ بدون آن «بارگذاری دوباره» همان ریلود است. تصمیم صریح: SW در M15.

## یک باگ جدی که پیش از تگ پیدا شد (advisor) و رفع شد
snapshot اول فقط رجیسترها و حالت Yjs را حمل می‌کرد، ولی رویدادها (نسخه‌های صفحه، مرور کارت) opهای همان موجودیت‌اند (`doc = ent`)؛ پس pull فشرده آن‌ها را پنهان می‌کرد و هرس بعد از ۳۰ روز برای همیشه پاک می‌کرد (تاریخچهٔ صفحه و برنامهٔ مرور کارت‌های پرمرور از دستگاه‌های تازه می‌رفت). حالا payload `snap` **رویدادهای موجودیت را هم** می‌برد (`putEvent`، تغییرناپذیر و idempotent)؛ اگر snapshot از یک op بزرگ‌تر شود آن سند **رد می‌شود** و تاریخچه هرگز برای جا شدن حذف نمی‌شود. آزمون روی سرور واقعی (صفحهٔ ۱۲۰ ویرایش + دو نسخه + کارت با سه مرور): دستگاه تازه از لاگ فشرده **همان تاریخچه و همان زمان‌بندی** را دارد. **کنترل:** با پاک کردن events از snapshot همین آزمون **می‌شکند**. و `Snapshotter` دیگر با یک سند بزرگ متوقف نمی‌شود و `snapshotAt` همیشه نوشته می‌شود.

## نتایج (اجرا شده)
| معیار | نتیجه |
|---|---|
| دستگاه تازه با pull فشرده همان سند را می‌سازد | سرور Go واقعی: ۱۵۰ ویرایش یک صفحه + snapshot؛ دستگاه تازه < ۱۰ op می‌کشد (نه ۱۵۰+) و متن و عنوان **یکسان** است |
| op با sv بالا هرگز با snapshot پنهان نمی‌شود | Go: opی با sv ۲ پشت snapshot با sv ۱ در pull فشرده می‌آید |
| op برای doc حذف‌شده هرگز آن را زنده نمی‌کند (آفلاین) | سرور واقعی: دستگاه دیرآمده opِ پیش از purge را می‌فرستد ← `purged`، از outbox می‌رود، و purge به آن دستگاه می‌رسد؛ سرور فقط opِ purge را برای آن doc نگه می‌دارد |
| هرس هیچ op پوشش‌نداده‌ای را حذف نمی‌کند | Go: **۶۰ تاریخچهٔ تصادفی** (۶۰ op، ۳ سند، sv ۱–۲، snapshotهای تصادفی، گذر زمان): حذف‌شده‌ها **دقیقاً** مجموعهٔ قاعده‌اند، نه کمتر و نه بیشتر (با کنترل: ≥ ۱۰۰ حذف و ≥ ۱۰۰ snapshot در مجموع). **fast-check نیست؛ Go با seed** چون هرس در سرور Go است |
| snapshot نمی‌تواند چیزی را بپوشاند که سرور ندارد | `400 bad_cov` (Go) |
| `410` و resync | Go (جاهای حذف‌شده → resync، pull از ۰ همیشه) + core (کلاینت cursor را صفر و فشرده می‌کشد) |
| snapshot فقط در شرایط امن | core: cursor ۰، head بالاتر، inbox پر ← null؛ فقط بعد از همه‌چیز می‌نویسد |
| converge | `pnpm converge`: ۵۰ seed، ۱۰۰٬۰۰۰ op، **converged: yes** (توجه: harness converge خودش snapshot/هرس را نمی‌زند؛ آن‌ها با آزمون‌های بالا) |
| e2e | purge در دو مرورگر: صفحه در هر دو فراموش می‌شود و روی سرور فقط opِ purge می‌ماند |
| دسکتاپ | `test:conformance` ۲۳/۲۳ (شامل `purgeEntity` روی SQLite)، `test:ui` سبز با پوستهٔ جدید |
| **کل (سه موتور)** | Playwright **Chromium + WebKit + Firefox: ۱۲۱ سبز، ۱۱ skip عمدی، ۰ شکست**؛ `test:engines` (Chromium+WebKit دو دستگاه) و `prod-csp-blocks` (سه موتور) سبز؛ `pnpm check` exit 0؛ `go test -race` سبز؛ vitest: core ۱۱۰، bundle ۸، converge ۷ |
| یادداشت | آزمون موبایل WebKit با پوستهٔ جدید شکست خورد (پنل صفحه‌ها روی محتوا باز بود و یک دکمهٔ جدول <۲۴px): پنل مثل اپ قدیمی در ≤۷۶۰px کشو با دکمهٔ نوار بالا شد و دکمه درست شد |

## اندازه‌گیری pull اولیه (localhost، سرور Go، ۲٬۰۰۰ سند × ۲۵ ویرایش)
| | op | حجم | زمان (localhost) |
|---|---|---|---|
| لاگ کامل | ۵۲٬۰۰۰ | **۲۳٫۹MB** | ۰٫۲ث |
| pull فشرده با snapshot | ۲٬۰۰۰ | **۸٫۲MB** | ۰٫۳ث |

حجم **۶۵٪ کمتر** و ۲۶ برابر opِ کمتر برای اعمال در کلاینت (هزینهٔ اصلی). زمان localhost گمراه‌کننده است (شبکه صفر و سرور snapshot را با SQL مشتق پنهان می‌کند). **سربار base64 payload: ×۱٫۳۳۸** (مطابق ۴/۳). iPhone و شبکهٔ واقعی با مالک.

## محدودیت‌ها
- **هرس ۳۰ روزه در عمل روی ساعت واقعی سنجیده نشد** (فقط با ساعت جعلی در Go)؛ بکاپ روزانه پیش از آن می‌رود.
- snapshotهای قدیمی‌تر هرس نمی‌شوند (فقط opهای معمولی)؛ هر snapshot تازه‌تر روی قبلی‌اش حساب می‌شود.
- رویدادهای مرور فلش‌کارت موجودیتِ کارت‌اند، نه صفحه؛ purge صفحه آن‌ها را حذف نمی‌کند.
- کلاینت قدیمی‌تر از این مرحله که `pg` بفرستد ندارد؛ سرور قدیمی `pg` را `bad_envelope` می‌گیرد (opِ purge در quarantine). همهٔ دستگاه‌ها و سرور باید یک‌جا به‌روز شوند.
- 426 با SW نیامد (بالا).
