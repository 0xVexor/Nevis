# Golden fixtures و قاعدهٔ نسخهٔ schema

## یک ثابت
`SV` فقط در `packages/protocol/src/version.ts` نوشته می‌شود (`@nevis/schema` آن را دوباره export می‌کند). هیچ‌جا عدد خام `sv: 1` نیست؛ همهٔ کلاینت‌ها، harness، صفحه‌های دسکتاپ و آزمون‌ها `SV` را import می‌کنند. آزمون سرور/وب که «نسخهٔ جدیدتر» می‌خواهد از `SV + 1` استفاده می‌کند.

## fixture چیست
`packages/schema/fixtures/sv<N>/<name>.json`: `{ name, sv, update (base64 از encodeStateAsUpdate، V1)، sha256 (بایت‌ها)، projection (JSON ProseMirror با پیش‌فرض‌ها) }`. با `scripts/capture-golden.ts` **یک بار** برای هر نسخه گرفته می‌شود و با پرچم «بازنویسی نکن» نوشته می‌شود؛ هیچ آزمونی آن‌ها را دوباره نمی‌سازد. `golden.test.ts` SHA-256 هر فایل را با مقدار ثبت‌شده می‌سنجد (بازنویسی بی‌صدا شکست می‌خورد).

## چه چیزی را می‌سنجد (قاعدهٔ مقایسه)
سندی که با schema **قدیمی‌تر** نوشته شده باید با schema **فعلی** به همان صفحه project شود، با مقایسهٔ `dropDefaults(projection)`: هر attribute که برابر پیش‌فرض schema است از دو طرف حذف می‌شود. یعنی:
- schema بعدی می‌تواند **attribute تازه (با پیش‌فرض غیر null) و گرهٔ تازه** اضافه کند بدون اینکه fixtureهای قدیمی باطل شوند یا دوباره ساخته شوند؛
- تغییر معنای یک attribute یا حذف آن، یا تغییر متن/ساختار یک سند قدیمی = شکست.
آزمون «غیرتوخالی» نشان می‌دهد تغییر یک attribute غیرپیش‌فرض واقعاً تفاوت است.

## چه زمانی `SV` بالا می‌رود
ADR-0002: هر تغییر schema = `SV + 1` و یک fixture. در عمل برای **هر milestone که schema را عوض می‌کند، یک بار**: `SV` در شروع کار schema آن milestone بالا می‌رود (برای M8a: ۱ → ۲) و تا برچسب milestone ثابت می‌ماند؛ گروه‌های بلوکِ داخل همان milestone **فقط افزایشی** (گرهٔ جدید، attribute جدید با پیش‌فرض) هستند و commitهای میانی منتشر نمی‌شوند. دلیل: داده‌ای با `sv = N` تا برچسب milestone بیرون از آزمون‌ها وجود ندارد. بعد از برچسب، schema آن `SV` منجمد است؛ هر تغییر بعدی `SV + 1` می‌خواهد.

## اثر بالا رفتن `SV` روی دستگاه‌های قدیمی‌تر
هر envelope `sv` نویسنده‌اش را دارد و `applyEnvelope` هر op با `sv` بزرگ‌تر از `sv` خواننده را **نگه می‌دارد (held)** و اعمال نمی‌کند؛ این شامل ویرایش‌های ساده فیلدها هم می‌شود، نه فقط بلوک‌های جدید. پس بعد از بالا رفتن `SV`: دستگاهی که هنوز نسخهٔ قدیمی را دارد (تب باز، باینری قدیمی دسکتاپ) تغییرات دستگاه‌های جدید را نمی‌بیند تا به‌روز شود، و سندی که `max_sv` آن بیشتر باشد در ادیتور باز نمی‌شود (پیام «به‌روزرسانی لازم»). آزمون‌های همگرایی دسکتاپ+وب باید هر دو را با هم build کنند.

## op بزرگ
یک op بزرگ‌تر از `MAX_P_CHARS` (۱٫۵M نویسه) را سرور برای همیشه رد می‌کند (400 دائمی)؛ بدون محافظت یک op مسموم کل outbox را برای همیشه می‌بندد. محافظت‌ها: (۱) `Client` قبل از نوشتن هر چیز `OpTooLargeError` می‌دهد؛ (۲) `DocHandle` ویرایشی را که از یک update بزرگ‌تر می‌شود با `onTooLarge` و `diverged` گزارش می‌دهد و دوباره تلاش نمی‌کند؛ (۳) اگر کلاینت قدیمی‌تر چنین opی ساخته باشد، موتور بعد از 400 دائمی opها را یکی‌یکی می‌فرستد و opِ رد‌شده را با دلیل به quarantine (seq منفی) می‌برد و `rejected` را گزارش می‌دهد. `data:` image هرگز در attribute نمی‌رود (تا M9 فقط placeholder).
