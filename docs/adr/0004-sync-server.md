# ADR-0004 — سرور همگام‌سازی Nevis (جایگزین Google Drive)

- وضعیت: **پذیرفته‌شده**؛ بخش «سینک با درایو» در ADR-0003 را جایگزین می‌کند. موتور سه‌طرفه، حفاظ‌های حذف و قواعد Vault همان می‌مانند.
- تاریخ: 2026-10-25

## زمینه

سینک با Google Drive برای کاربران ایران کار نمی‌کرد: ورود با Google فیلتر است و دسترسی به Drive قطع‌ووصل می‌شود. هر دستگاه هم فقط هر دقیقه یک لیست کامل از Drive می‌گرفت، پس تغییر یک دستگاه چند ده ثانیه تا چند دقیقه دیرتر به بقیه می‌رسید. نتیجه خواسته‌شده: تغییر یک دستگاه ظرف حدود یک ثانیه به دستگاه‌های دیگر برسد (نه تایپ همزمان)، اینترنت ناپایدار چیزی را خراب یا گم نکند، و برای چند کاربر کار کند، **بدون ایمیل و بدون پیامک** (خرید سرویس ارسال ایمیل ممکن نیست).

## تصمیم

یک سرور کوچک (پوشه‌ی [`server/`](../../server/)، Node.js روی Liara، فایل‌ها روی S3، فهرست در SQLite) و یک `Remote` جدید برای موتور سینک موجود ([`hub.rs`](../../spike/tiptap/src-tauri/src/sync/hub.rs)). موتور (`sync_once`، `plan`، قطع‌کننده‌ی حذف، سطل سینک، ادغام صفحه‌ها و kvها) دست‌نخورده ماند و همه‌ی ۳۸ تست قبلی‌اش سبز ماند؛ فقط «ابر» عوض شد. Google و Drive از برنامه برداشته شد.

```
دستگاه A ──commit──▶ ┌───────────────────────────┐ ◀──pull── دستگاه B
          (CAS)      │ API  → SQLite (rev, seq)  │
دستگاه A ◀──head──── │ long-poll hub             │ ──head──▶ دستگاه B
                     └─────────────┬─────────────┘
                                   ▼  blobها (SHA-256) + بکاپ فهرست
                                   S3
```

### مدل
- هر Vault یک `seq` دارد که فقط بالا می‌رود؛ هر مسیر `rev` = `seq` آخرین تغییرش. «همه‌ی تغییرها بعد از N» همان `files WHERE rev > N` است. ترتیب رویدادها ترتیب `seq` است، نه ساعت دستگاه.
- حذف یک رخداد است (tombstone با `rev` خودش)، نه غیبت. tombstone و نسخه‌های قدیمی ۳۰ روز می‌مانند و بعد پاک می‌شوند؛ دستگاهی که از آن عقب‌تر است `410` می‌گیرد و از نو شروع می‌کند (بدون حذف).
- هر بار که سرور از بکاپ برگردد `epoch` عوض می‌شود؛ دستگاه‌ها می‌فهمند و فقط می‌افزایند، نه حذف.
- شناسه‌ی فایل در کلاینت `"<rev>:<path>"` است؛ موتور آن را رشته‌ی مبهم می‌بیند.

### پروتکل (خلاصه؛ کامل در [server/README.md](../../server/README.md))
1. **محتوا اول:** `PUT /blobs/<sha256>` (idempotent، با `Content-Range` قابل ادامه). سرور هش را دوباره حساب می‌کند و فقط اگر برابر نام باشد می‌پذیرد.
2. **بعد commit:** `POST /commit { op_id, ops:[{put|delete, path, base_rev, sha256}] }`. هر op شرطی است: اگر مسیر از `base_rev` جلوتر رفته باشد `conflict` با وضعیت فعلی برمی‌گردد و چیزی رونویسی نمی‌شود. `op_id` تکراری همان جواب قبلی را می‌دهد.
3. **خبر:** `GET /state?since=N&wait=25` یک درخواست باز می‌ماند و لحظه‌ای که دستگاه دیگری commit کند جواب می‌دهد. (long-poll، نه WebSocket: از هر پروکسی‌ای که HTTPS را رد کند رد می‌شود و بعد از قطع، اتصال دوباره ساده است.)
4. **فقط تفاوت:** کلاینت یک آینه‌ی محلی از لیست سرور دارد (`Cache`) و با `GET /changes?since=` به‌روزش می‌کند؛ `root` (هش همه‌ی `(path, md5)` زنده) آینه را راستی‌آزمایی می‌کند و آینه‌ی خراب خودش را بازسازی می‌کند، چون فایلی که از آینه افتاده باشد برای موتور «حذف‌شده» به نظر می‌رسد.

### حساب بدون ایمیل
نام کاربری + رمز (scrypt) + **کلید بازیابی** ۱۰۰ بیتی که یک‌بار نشان داده می‌شود و با آن رمز عوض می‌شود. ثبت‌نام باید یک اثبات کار (proof of work) و در حالت پیش‌فرض یک کد دعوت داشته باشد. هر دستگاه token جدا دارد (فقط هشش روی سرور) که از صفحه‌ی حساب باطل می‌شود. ورود اشتباه هم per-user هم per-IP محدود می‌شود (پشت NAT مشترک موبایل، محدودیت اصلی per-user است). حذف حساب ۳۰ روز مهلت دارد.

### رفتار روی اینترنت ناپایدار
- ویرایش هیچ‌وقت منتظر شبکه نمی‌ماند؛ اول روی دیسک می‌نشیند و موتور بعداً می‌فرستد.
- هر درخواست امن است که تکرار شود (blob با هش، commit با `op_id`)؛ قطع شدن وسط کار فقط وقت می‌خرد. connect timeout ۱۰ ثانیه؛ بعد از شکست، تلاش‌ها یک‌بار و با backoff ۳، ۶، ۱۲، ۲۰ ثانیه است تا ثانیه‌ها در retry نسوزند.
- وضعیت «آفلاین» جدا از «خطا» نشان داده می‌شود؛ ناظر long-poll بعد از قطع با پاسخ فوری (`wait=0`) برگشتن اتصال را می‌فهمد و همان لحظه سینک را بیدار می‌کند.
- یک سینک ناقص چیزی نمی‌شکند: state بعد از هر ۲۵ اکشن ذخیره می‌شود و آینه فقط آینه است (قبل از هر سینک دوباره به سرور می‌رسد).

## قواعد (فهرست کوتاه)
بدون حذف مستقیم؛ نبودن مدرک حذف نیست؛ هر نوشتن شرطی است؛ بازنده‌ی conflict دور ریخته نمی‌شود؛ محتوا قبل از commit کامل و با هش تأیید شده است؛ نوشتن محلی atomic است؛ ترتیب با `seq`؛ هر عملیات idempotent؛ echo خودی دوباره اعمال نمی‌شود؛ preflight (marker، `vault_id`، epoch)؛ epoch/`since` قدیمی → baseline بدون حذف؛ قطع‌کننده‌ی حذف گروهی (کلاینت و سرور)؛ فایل نامعلوم دست‌نخورده می‌ماند؛ مسیرها امن و بدون تضاد حروف بزرگ/کوچک؛ سهمیه و سقف اندازه؛ token جدا برای هر دستگاه. فهرست کامل با دلیل‌ها و همه‌ی سناریوها و لبه‌ها در سند طراحی همراه این ADR است.

## تست
- سرور: ۵۹ تست `node:test` (حساب، CAS، tombstone و زنده‌شدن دوباره، atomic، حذف گروهی، مسیرها، blob تکه‌تکه، سهمیه، جداسازی کاربران، long-poll، housekeeping، بکاپ و بازیابی، قفل تک‌نمونه).
- کلاینت: ۳۸ تست Rust (موتور و کمکی‌ها، از جمله هش `root` که با سرور یکی است) و ۹ تست سرتاسری روی سرور واقعی (`cargo test e2e -- --ignored`): رفت‌وبرگشت، دو صفحه‌ی همزمان، یک صفحه‌ی همزمان (قدیمی‌تر در history)، حذف، پیوست ۵ مگابایتی تکه‌تکه، کار آفلاین، سرور از دست‌رفته، آینه‌ی خراب، Vault حذف‌شده از سرور.
- برنامه‌ی دسکتاپ واقعی با دستگاه دوم روی HTTP (روی یک کامپیوتر، پس بدون تأخیر شبکه): ذخیره در برنامه → دیده شدن در دستگاه دیگر حدود ۰٫۶ ثانیه؛ تغییر دستگاه دیگر → فایل در پوشه‌ی برنامه حدود ۰٫۳ تا ۱ ثانیه؛ قطع سرور → «آفلاین» و بعد از برگشتن سرور ارسال ویرایش‌های آفلاین کمتر از یک ثانیه.

## محدودیت‌ها و کارهای بعد
- یک نمونه‌ی سرور (قفل heartbeat روی S3 از دو نمونه جلوگیری می‌کند).
- محتوا رمزنگاری سرتاسری نیست؛ اپراتور سرور می‌تواند آن را بخواند (در سیاست حریم خصوصی گفته شده). مدل blobهای محتوا-محور مانع افزودن E2E بعداً نیست.
- Vault مشترک بین چند کاربر و ویرایش همزمان یک صفحه (CRDT) هنوز نیست.
- موتور هر فایل را جدا commit می‌کند (دو درخواست برای هر فایل). برای اولین سینک Vaultهای خیلی بزرگ، commit دسته‌ای (`ops` تا ۲۰۰ تا) را می‌شود به موتور اضافه کرد؛ API از الان آماده است.
- ادغام سه‌طرفه‌ی سطح بلوک برای یک صفحه (به‌جای «جدیدتر می‌ماند و قدیمی‌تر در history»).
