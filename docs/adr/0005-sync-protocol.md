# ADR-0005: پروتکل همگام‌سازی

- وضعیت: **تصمیم‌شده، منتظر spike M2** (همگرایی و idempotency)
- اطمینان: ۸۰٪
- تاریخ: 2026-11-20
- مرتبط: ADR-0001، ADR-0002، ADR-0006، ADR-0008، ADR-0011؛ تحقیق: R4 §2 و §4 و §7، R7 §6، `storage-and-sync-options.md` §D-1

## زمینه
- سرور ساده، Go، بدون منطق ادغام، و از روز اول آماده برای رمزنگاری (payload مات).
- الگوی تکرارشونده در سیستم‌های بالغ: push دسته‌ای idempotent با شناسهٔ op، pull با cursor عددی سرور، snapshot برای شروع سریع (R4 §2).

## گزینه‌ها
| گزینه | نتیجه |
|---|---|
| پروتکل sync خود Yjs (y-websocket/Hocuspocus) | رد: فقط Yjs را حل می‌کند، لاگ seq ندارد، برای رجیسترها کاری نمی‌کند (R4 §1). |
| Merkle/HLC مثل Actual | رد: پیچیده‌تر از cursor سرور وقتی سرور مرکزی داریم. |
| **لاگ append-only per workspace با `seq` سرور + push idempotent + pull با cursor + long-poll** | **انتخاب.** |

## تصمیم
### envelope (تنها چیزی که سرور می‌خواند)
```json
{"v":1,"op":"019a8f3c-2b10-7c3e-8f00-1a2b3c4d5e6f","ws":"019a…","doc":"019a…","dev":"019a…",
 "t":"019a8f3c2b10-0000-019a…","sv":1,"kid":0,"p":"AQB7InNldCI6…"}
```
| فیلد | نوع | معنا |
|---|---|---|
| `v` | int | نسخهٔ envelope (`1`) |
| `op` | UUIDv7 | شناسهٔ op؛ کلید idempotency |
| `ws` | UUIDv7 | workspace (باید با URL یکی باشد) |
| `doc` | UUIDv7 | موجودیتی که op به آن تعلق دارد (برای snapshot و purge) |
| `dev` | UUIDv7 | دستگاه نویسنده |
| `t` | HLC | زمان منطقی op (برای بررسی انحراف ساعت) |
| `sv` | int | نسخهٔ schema نویسنده |
| `kid` | int | `0` = بدون رمز؛ >0 = شناسهٔ کلید (ADR-0011) |
| `n` | base64url | nonce؛ فقط وقتی `kid>0` (در v1 وجود ندارد) |
| `p` | base64url بدون padding | **بایت‌های مات payload** |
| `cov` | int | فقط در op snapshot (پایین‌تر) |

سرور هیچ فیلد دیگری را نمی‌پذیرد (`400 bad_envelope`) و `p` را هرگز decode نمی‌کند.

### payload (فقط کلاینت می‌فهمد)
`p` = یک فریم دودویی: **بایت اول = نوع**، بقیه = داده.
| نوع | نام | داده |
|---|---|---|
| `0x01` | `rec` | JSON UTF-8: `{"kind":"page","set":{"title":"…","sortKey":"a0x9Kf"},"h":"<hlc>"}` (`kind` فقط در op ساخت) |
| `0x02` | `yupd` | update Yjs V1 خام برای بدنهٔ `doc` |
| `0x03` | `evt` | JSON UTF-8: `{"id":"…","kind":"review","h":"<hlc>","body":{…}}` |
| `0x04` | `snap` | `u32be` طول JSON + JSON حالت فیلدها `{"fields":{"title":["…","<hlc>"]}}` + state Yjs V1 (اگر بدنه دارد) |
| `0x05` | `purge` | خالی (نشانگر حذف دائمی؛ M13) |
دلیل فریم دودویی به‌جای JSON: جلوگیری از base64 دوبل روی update Yjs.

### push
`POST /v1/ws/{ws}/ops` — بدنه: `{"ops":[<envelope>…]}`؛ حداکثر ۵۰۰ op یا ۴MB.
- سرور کل دسته را در **یک تراکنش** ثبت می‌کند و به هر op تازه `seq` بعدی workspace را می‌دهد.
- **idempotency:** `UNIQUE(ws, op)`. op تکراری با بایت‌های یکسان (مقایسهٔ SHA-256 envelope) → همان `seq` قبلی با وضعیت `dup`. **op تکراری با بایت متفاوت → `409 op_conflict`** و کل دسته رد (نشانهٔ باگ کلاینت؛ هرگز بی‌صدا پذیرفته نمی‌شود).
- op برای `doc` حذف‌شدهٔ دائمی → وضعیت `purged` (کلاینت آن را از outbox حذف می‌کند).
- `t` بیش از ۱۰ دقیقه جلوتر از ساعت سرور → `422 clock_ahead` برای کل دسته. opهای دستهٔ ردشده **هرگز پذیرفته نشده‌اند**؛ بعد از درست شدن ساعت، کلاینت opهای outbox با `t` آینده را با `op` و HLC تازه دوباره می‌سازد (محتوا همان) تا دستگاه منتظر رسیدن زمان واقعی نماند؛ در همان تراکنش `meta.hlc` به زمان درست برمی‌گردد و رجیسترهای محلی که HLC آینده دارند با HLC تازه بازنویسی می‌شوند (این opها هرگز از دستگاه بیرون نرفته‌اند، پس یکنواختی HLC برای هیچ دستگاه دیگری نمی‌شکند). این تنها حالتی است که بایت‌های outbox بازسازی می‌شوند؛ آزمون آن در M4.
- پاسخ: `{"results":[{"op":"…","seq":1234,"status":"ok"|"dup"|"purged"}],"head":1240}`.
- کلاینت ردیف outbox را فقط بعد از دیدن `seq` حذف می‌کند. outbox **بایت‌های envelope را همان‌طور که اولین بار سریال شد** نگه می‌دارد، پس ارسال دوباره همیشه بایت یکسان است.
- opی که به blob ارجاع دارد تا آپلود همهٔ blobهایش تمام نشده ارسال نمی‌شود (ستون محلی `outbox.blobs`).

### pull
`GET /v1/ws/{ws}/ops?after=<seq>&limit=<n≤1000>&wait=<0..25>`
- پاسخ: `{"ops":[{"seq":1235,"by":"<accountId>","rt":1732089600123,"env":{…}}],"head":1240,"more":false}`.
- `by` (حساب نویسنده، از نشست) و `rt` (زمان دریافت سرور) را **سرور** می‌گذارد؛ ادعای کلاینت نیستند.
- opهای خود دستگاه هم برمی‌گردند (اعمال دوباره بی‌اثر است؛ ساده‌تر از فیلتر).
- **long-poll:** اگر `after >= head` و `wait>0`، سرور تا `wait` ثانیه نگه می‌دارد و با اولین commit جواب می‌دهد. این همان «کانال لحظه‌ای» v1 است؛ از هر proxy عبور می‌کند. WebSocket فقط برای awareness در هم‌نویسی (ADR-0011).
- کلاینت: opها را در `inbox` می‌نویسد و `cursor` را در همان تراکنش جلو می‌برد (ADR-0001)، بعد اعمال می‌کند.
- **ناوردایی ترتیب:** هیچ pullی نباید `seq` بالاتر را ببیند در حالی که `seq` پایین‌تری بعداً commit شود. سرور این را با **یک نویسندهٔ واحد** تضمین می‌کند (ADR-0006) و آزمون هم‌زمانی آن را می‌سنجد.

### اعمال (کلاینت)
- ترتیب اعمال روی نتیجه اثر ندارد (Yjs و LWW جابه‌جایی‌پذیر و idempotentاند). `seq` فقط برای cursor است.
- op با `sv` بالاتر از کلاینت در inbox می‌ماند (ADR-0002) و **در همان تراکنش `doc_state.max_sv` آن doc بالا می‌رود** تا سند به‌جای باز شدن با محتوای کهنه، «به‌روزرسانی لازم» نشان دهد.
- op نامعتبر (JSON خراب، فریم ناشناخته): در جدول محلی `quarantine` نگه داشته و گزارش می‌شود؛ cursor جلو می‌رود؛ هرگز اپ را متوقف نمی‌کند.

### snapshot (v1: فقط شتاب‌دهنده، بدون حذف)
- کلاینت برای `doc`ی که opهای زیاد دارد یک op با payload نوع `snap` از همان `POST ops` می‌فرستد. envelope این op یک فیلد اختیاری اضافه دارد: `"cov": <seq>` = بزرگ‌ترین `S` به‌طوری که **همهٔ** opهای آن doc با `seq ≤ S` در کلاینت اعمال شده باشند. opی از همان doc که در inbox نگه داشته شده (`sv` بالاتر) یا در `quarantine` است، `cov` را به زیر `seq` خودش محدود می‌کند. اگر کلاینت op محلی ارسال‌نشده برای آن doc دارد، snapshot نمی‌سازد. (بدون این قاعده، pull فشرده opی را که در snapshot نیست برای همیشه از دستگاه‌های تازه پنهان می‌کند.) سرور `(ws, doc, seq, cov)` را در جدول `snapshot` ثبت می‌کند. `cov` فقط در opهای snapshot مجاز است.
- **pull فشرده** برای دستگاه تازه: `GET …/ops?after=0&compact=1` برای هر `doc` با snapshot، opهای `seq ≤ cov` آن doc را رد می‌کند و snapshot را می‌دهد. سرور برای این کار فقط به سربرگ `doc` نیاز دارد.
- **در v1 هیچ opی فیزیکی حذف نمی‌شود.** حذف فیزیکی و `410 resync_required` در milestone جدا با آزمون‌های خودش (M13).

### نسخه و قطع ارتباط
- هر درخواست سربرگ `Nevis-Proto: 1` و `Nevis-Device: <deviceId>` دارد. سرور اگر `proto < minProto` یا `sv < minSv` → `426` با `{"minProto":1,"minSv":1}`؛ کلاینت ارسال را متوقف و پیام «به‌روزرسانی لازم» نشان می‌دهد؛ دادهٔ محلی دست‌نخورده.
- خطاها: `{"error":{"code":"…","message":"…","retryable":bool}}`؛ `429` با `Retry-After`. کلاینت backoff نمایی با jitter (۱s تا ۵ دقیقه).

## پیامدها
- سرور فقط سربرگ را می‌فهمد؛ همان سرور برای حالت رمزنگاری‌شده کار می‌کند.
- هر دستگاه جدید بدون snapshot کل لاگ را می‌کشد؛ برای دادهٔ یک کاربر در v1 پذیرفتنی است، با snapshot (M13) کوتاه می‌شود.

## چه چیزی تصمیم را برمی‌گرداند (M2)
- harness همگرایی (۳ replica، ۲۰۰ seed، تحویل تکراری/بی‌ترتیب/گم‌شده، crash بین نوشتن محلی و ارسال) هر واگرایی نشان دهد.
- ارسال دوبارهٔ یک دسته ۱۰ بار `seq` یا حالت را تغییر دهد.
- آزمون هم‌زمانی سرور (۸ pusher و ۴ puller، ۱۰k op) گپ دیده‌شده‌ای نشان دهد که بعداً پر شود.
