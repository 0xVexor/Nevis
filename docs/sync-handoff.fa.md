# سینک با سرور شخصی: وضعیت، راه‌اندازی و کارهای مانده

آخرین به‌روزرسانی: ۲۸ آبان ۱۴۰۵ (۱۹ نوامبر ۲۰۲۶). این سند برای ادامهٔ کار است: چه ساخته شده، چطور اجرا و آزمایش می‌شود، و چه چیزی مانده.

## هدف

هر کاربر داده‌های خودش را بین دستگاه‌های خودش یکی نگه دارد، از راه سروری که خودش اجرا می‌کند. **همکاری و اشتراک سند بین چند نفر هدف نیست.** هر نفر یک حساب و یک فضای جدا دارد. ویرایش آفلاین باید کار کند و هیچ متنی بی‌صدا از بین نرود.

## چه چیزی کجاست

- `server/`: سرور Go. باینری تک‌فایل، SQLite خالص Go (`modernc.org/sqlite`، بدون cgo)، فایل‌ها روی دیسک. راهنمای کامل در `server/README.md` (تنظیمات، systemd، Caddy، پروتکل).
- `spike/tiptap/src-tauri/src/sync/`: موتور سینک. `mod.rs` (مقایسهٔ سه‌طرفه، قطع‌کنندهٔ حذف، سطل سینک)، `hub.rs` (کلاینت سرور)، `account.rs` (حساب)، `snapshot.rs` (tombstone و کمکی‌های فایل)، `sync-paths.json` (قرارداد مسیرها).
- `spike/tiptap/src-tauri/src/sync_app.rs`: اتصال به برنامه. thread سینک، thread شنونده (long poll) و دستورهای تنظیمات.
- `spike/tiptap/src/sync/`: `client.ts` (فراخوانی دستورها، ترجمهٔ خطاها) و `SyncSettings.tsx` (صفحهٔ تنظیمات).
- `.github/workflows/ci.yml`: jobهای `server` و `sync-e2e`.
- طراحی: [ADR-0004](adr/0004-sync-server.md) (در `dev` است). `docs/sync-design-research.md` هنوز در `dev` نیست (روی شاخهٔ `sync-server-and-accounts`).

## اصول طراحی

- **سرور کور:** سرور فقط فایل‌ها و شماره‌ترتیب را می‌داند و هیچ‌وقت محتوا را ادغام نمی‌کند. شمارهٔ ترتیب سمت سرور (`seq`) به ساعت دستگاه‌ها وابسته نیست.
- **هر نوشتن شرطی است:** هر commit نسخهٔ پایه (`base_rev`) را می‌فرستد و اگر مسیر جلوتر رفته باشد رد می‌شود. تکرار یک درخواست امن است (`op_id`).
- **محتوا اول، commit بعد:** فایل‌ها با هش SHA-256 آپلود می‌شوند و سرور هش را دوباره حساب می‌کند.
- **تداخل:** مقایسهٔ سه‌طرفه روی فایل. بازنده دور ریخته نمی‌شود و در `history/` می‌ماند.
- **حذف:** هیچ‌وقت حذف مستقیم نیست. tombstone و سطل سینک (۷ روز، `TRASH_KEEP_MS` در `vault.rs`؛ ۳۰ روز نگه‌داری سمت سرور است). حذف گروهی (بیش از ۵ فایل یا ۲۰٪) تا تأیید کاربر می‌ماند. نبودن یک فایل مدرک حذف نیست.
- **سرور برگشته از بکاپ** `epoch` جدید می‌گیرد و دستگاه‌ها فقط می‌افزایند، حذف نمی‌کنند. دستگاهی که خیلی عقب است `410` می‌گیرد و از نو شروع می‌کند، بدون حذف.
- نسخهٔ وب برنامه سینک ندارد. فعلاً فقط دسکتاپ.

## نام‌هایی که کلاینت و سرور باید یکی باشند

- `/v1/health` باید `"name": "nevis-sync"` بدهد (و `capabilities` شامل `database_sync` باشد).
- سرآیند نسخهٔ پروتکل: `x-nevis-api`. سرور سرآیند قدیمی `X-Noviq-Api` را هم می‌پذیرد.
- فایل نشانهٔ فضای کاری: `.nevis/vault.json`.
- برنامه آدرس پیش‌فرض سرور ندارد. اگر بیلدی بخواهد آدرس ثابت داشته باشد، متغیر زمان بیلد `NEVIS_SERVER` را بدهید.
- `http://` فقط برای `localhost` پذیرفته می‌شود. برای سرور واقعی HTTPS لازم است.

## راه‌اندازی سرور

روی سرور Go (نسخهٔ ۱٫۲۶ به بالا) و git لازم است.

```bash
git clone https://github.com/0xVexor/Nevis.git
cd Nevis/server
go build -o nevis-server ./cmd/nevis-server
```

اجرای آزمایشی:

```bash
SESSION_SECRET=$(openssl rand -hex 24) REGISTRATION=open DATA_DIR=/var/lib/nevis PORT=3000 ./nevis-server
```

برای استفادهٔ واقعی آن را با systemd اجرا کنید و پشت Caddy یا nginx با HTTPS بگذارید. نمونهٔ کامل و جدول همهٔ تنظیمات (`REGISTRATION`، `INVITE_CODES`، `QUOTA_MB`، `TRUST_PROXY`، `BACKUP_DELAY_SEC` و غیره) در `server/README.md` است. بعد از ساخت حساب اول، `REGISTRATION=invite` یا `closed` بگذارید.

بکاپ: سرور خودش با `VACUUM INTO` در `DATA_DIR/backup/` نسخه می‌گیرد، ولی **روی همان دیسک** و **فقط پایگاه‌داده، بدون فایل‌های `blobs/`**. بازیابی فقط پایگاه‌داده محتوای فایل‌های بعد از آن بکاپ را برنمی‌گرداند. کل `DATA_DIR` (پایگاه‌داده و blobs) را به خارج از میزبان بکاپ بگیرید. `nevis-server restore` پایگاه‌داده را جایگزین می‌کند و به هر Vault `epoch` تازه می‌دهد.

**حریم خصوصی:** سرور ساختار را نمی‌فهمد ولی رمزنگاری سرتاسری نیست؛ هر کس سرور را اجرا کند فایل‌ها (یادداشت، تصویر، پیوست) را بدون رمز می‌خواند. HTTPS، رمز کردن دیسک سرور و اعتماد به میزبان لازم است (جزئیات در ADR-0004).

## آزمایش دو دستگاه

1. بتای `1.2.0-beta.6` یا جدیدتر را نصب کنید (یا از شاخه build بگیرید تا کارهای `feature/sync-finish` را ببینید).
2. دستگاه اول: تنظیمات → Sync → آدرس سرور → «ساخت حساب». **کلید بازیابی** یک بار نشان داده می‌شود؛ ذخیره‌اش کنید. بعد «همگام‌سازی این فضای کاری» را روشن کنید.
3. دستگاه دوم: ورود با همان حساب → «فضاهای کاری روی سرور» → Download → یک پوشه انتخاب کنید.
4. موارد آزمایش:
   - ویرایش یک صفحه در یک دستگاه و دیدنش در دیگری (حدود یک ثانیه).
   - ویرایش آفلاین هر دو دستگاه روی یک صفحه: نسخهٔ بازنده باید در تاریخچهٔ صفحه بماند.
   - حذف یک صفحه و دیدن اثرش در دستگاه دیگر.
   - حذف گروهی: باید منتظر تأیید بماند.
   - عکس و ویدیو (فایل‌های بزرگ).
   - قطع اینترنت وسط سینک و وصل دوباره.
   - دیتابیس‌ها (پوشهٔ `databases/`). حدسی بود که نوع‌ها با کلاینت یکی‌اند؛ سرور فقط شکل مسیر را بررسی می‌کند.
5. فقط روی فضاهای کاری آزمایشی تست کنید، نه روی داده‌های اصلی.

## انجام‌شده

- بازسازی آینه با snapshot صفحه‌به‌صفحه (`GET /changes?snapshot=1`) وقتی سرور تاریخچه را فراموش کرده (۴۱۰).
- تشخیص برگشت به نسخهٔ قدیمی با حلقهٔ md5 محتواهای سینک‌شده (`Entry::seen`)؛ بازیابی یک کپی قدیمی پوشه حذف نمی‌سازد.
- tombstone محدودشده: فقط `pages/<id>.json` و رکوردهای `databases/` (و state صفحه با صفحه‌اش)؛ نبودنِ بدون tombstone فقط نگه داشته می‌شود.
- قواعد بازیابی پشتیبان قابل‌حمل (مورد قدیمی «tombstone در پشتیبان قابل‌حمل»): بازیابی نسخهٔ قدیمی‌تر حذف‌ها را نگه می‌دارد و بازنده در history می‌ماند.
- شکاف‌های state صفحه (قفل حذف، همزمانی دانلود و ذخیره) بسته شد؛ مهاجرت هنوز پشت پرچم `pageState` است و **نباید روشن شود** (بخش پایین).
- دستگاهی که bookkeeping را از دست داده صفحه‌ای را که دستگاه دیگر حذف کرده دوباره آپلود نمی‌کند و نگه می‌دارد (tombstoneهای سرور با `snapshot=1&deleted=1`).
- تشخیص پوشهٔ قدیمی‌تر بازگردانده‌شده با حلقهٔ ۸ محتوا، `updatedAt` صفحه و mtime (تحمل ۲ ثانیه) → تداخل از نوع `restore`.
- صفحه‌ای که جای دیگر پاک شده ولی اینجا باز است: ویرایش به‌صورت صفحهٔ تازهٔ «بازیابی‌شده: …» می‌ماند.
- بازندهٔ تداخل تا وقتی marker بازی به آن ارجاع می‌دهد trim نمی‌شود.
- حفاظ اختلاف ساعت: `updatedAt` بیش از ۱۰ دقیقه جلوتر از ساعت سرور فقط برای مقایسه محدود می‌شود؛ پرچم `clockSkew` در marker.
- marker تداخل (`history/conflicts/<pageId>/<cid>.json`)، نمای حل تداخل در همان صفحه و نشانگر سراسری سینک در نوار کناری.
- (هفت مورد بالا فقط با آزمون خودکار پوشش دارند؛ اجرای واقعی دو دستگاه انجام نشده.)
- سهمیه با احتساب آپلودهای در جریان، قفل ورود نرم‌تر، مهلت انتقال برای هر handler ([bd09673](https://github.com/0xVexor/Nevis/commit/bd09673)).
- رویداد `vault-changed` را برنامه از قبل مدیریت می‌کند (`src/platform/documentEnvironment.ts` به آن گوش می‌دهد)؛ دیگر کار رابطی مانده نیست.
- Rust روی ماشین توسعه نصب است و آزمون‌های e2e محلی روی سرور Go اجرا شد (۱۱ آزمون پاس).

## کارهای مانده

1. **آزمایش روی سرور واقعی و دو دستگاه واقعی** (بالا). ظاهر صفحهٔ Sync، از جمله بخش‌های تازهٔ `feature/sync-finish`، هنوز در برنامهٔ در حال اجرا دیده نشده.
2. **تگ انتشار:** بتای بعدی را مثل قبل بسازید (`node .github/scripts/bump-version.cjs <نسخه>` روی شاخه‌ای از `dev`، یادداشت در `docs/releases/`، PR به `dev`، تگ روی commit مربوط).
3. **ثبت‌نام و PoW:** تنظیم سختی (`POW_BITS`) و سیاست ثبت‌نام برای سرور واقعی.
4. **حذف دسته‌ای با `confirm_bulk`:** سرور پشتیبانی می‌کند ولی موتور هر فایل را جدا commit می‌کند. **عمداً انجام نشده:** این کار روش حذف کلاینت‌های منتشرشده را عوض می‌کند.
5. **دروازهٔ حداقل نسخهٔ کلاینت روی سرور.** الان فقط نسخهٔ پروتکل (`MinAPI`) اعمال می‌شود، نه نسخهٔ برنامه. پیش‌نیاز روشن کردن `pageState`.
6. **بکاپ blob خارج از میزبان.** بکاپ خود سرور روی همان دیسک است و blobها را ندارد؛ تا الان فقط توصیهٔ دستی (rsync کل `DATA_DIR`) هست.
7. **رمزنگاری سرتاسری (آینده).** ساخته نشده؛ بیت ۰ پرچم‌های سرآیند `NVPS` برای آن رزرو شده ولی استفاده نمی‌شود. تا آن موقع سرور باید قابل‌اعتماد فرض شود.
8. **آزمون‌هایی که بازبینی خواست و نوشته نشده‌اند ):** سه دستگاه، `kill -9` وسط سینک، اختلاف ساعت، راه‌اندازی دوبارهٔ سرور (۸ آزمون در این چهار دسته).
9. **تداخل صفحه‌هایی که Yjs ادغام می‌کند:** marker ندارند.
10. **نوع‌های تداخل `deleted-here` / `deleted-there`:** در فرمت marker پیش‌بینی شده، پیاده نشده.
11. **ادغام خودکار بلوک‌ها:** انجام شد (`sync/blockmerge.rs`) و فقط برای صفحه‌ها است. هنوز ادغام درون یک بلوک (دو کلمهٔ متفاوت در یک پاراگراف) نداریم: آن حالت تداخل می‌ماند و در نمای حل تداخل انتخاب می‌شود.
12. **نسخهٔ وب** سینک ندارد.
13. **پاک‌سازی tombstone محلی** فقط اگر روزی اندازه‌اش مسئله شد.
14. **پرچم انتشار:** در `spike/tiptap/release-features.json` مقدار `sync` الان `true` و `pageState` برابر `false` است. هر نسخه‌ای از `dev` تب Sync را دارد؛ برای خاموش کردن `sync` را `false` کنید.

## state صفحه (Yjs): هنوز روشن نکنید

دلیل‌ها (از بازبینی): بتاهای منتشرشدهٔ ۳ تا ۶ پوشهٔ `pages-state/` را نادیده می‌گیرند یا درست مدیریت نمی‌کنند و `pages/<id>.json` را ویرایش می‌کنند، پس بی‌صدا از هم جدا می‌شوند؛ برگرداندن پرچم فقط مهاجرت را متوقف می‌کند و صفحه‌های مهاجرت‌شده برنمی‌گردند؛ سازگاری با y-prosemirror آزموده نشده؛ عمق fuzz کم است؛ و سرور هنوز دروازهٔ حداقل نسخهٔ برنامه ندارد (این‌که بتاهای ۳ تا ۶ چه چیزی می‌فرستند در کد بررسی نشد). پیش از روشن کردن: دروازهٔ حداقل نسخه، آزمون واقعی دو و سه دستگاه، آزمون y-prosemirror، fuzz عمیق‌تر، تصمیم دربارهٔ مسیر برگشت، و تکلیف تداخل صفحه‌های ادغام‌شده با Yjs.

## کارهای عمومی مانده از قبل

- PR برگرداندن `main` به `dev` (بعد از release 1.1.0) هنوز ساخته نشده.
- release و تگ قدیمی `v1.0.0` را خودتان در GitHub حذف کنید.

- یک worktree باقی‌مانده از کار سرور Go در `.claude/worktrees/agent-a0dd3696968e22e75` هست: `git worktree remove` را روی آن بزنید.
- یک فایل `zig.exe` (کامپایلر C) در پوشهٔ موقت جلسه دانلود شد و **هرگز اجرا نشد**. پاکش کنید.

## نکته‌های کار با این مخزن

- Windows: فایل‌های کاری CRLF هستند و مخزن LF. در ویرایش خودکار فایل‌ها به این دقت کنید.
- روی این ماشین Rust نصب است و کد را می‌شود محلی ساخت و آزمود (e2e: `NEVIS_TEST_SERVER=http://localhost:3111 cargo test e2e -- --ignored --test-threads=1` در `src-tauri` با سرور Go در حال اجرا)؛ CI هم هر سه سیستم‌عامل را می‌سازد.
- log کامل CI را می‌توان در پنل مرورگر برنامه با آدرس `https://github.com/0xVexor/Nevis/commit/<sha>/checks/<id>/logs` خواند (اگر وارد GitHub شده باشید). API بدون توکن سریع محدود می‌شود.
- گیت: feature → `dev` با PR؛ `dev` → `main` برای نسخهٔ نهایی؛ تگ فقط روی commit درست (راهنما در `docs/git-flow.md`).
